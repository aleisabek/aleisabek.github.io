CASE-001SkillQuest

Covers

The problem

Fixed question banks get memorized, and a quiz score doesn't show whether you can fix a broken system. I wanted daily practice that builds job skills and measures them honestly.

What I built

  1. A path from foundations to specialization.Short lessons start with Linux, networking, security and IT support, then open into cloud and offensive security once the basics are solid.
  2. Questions that can't be memorized.Subnetting, permissions, IAM policy and firewall problems are generated fresh each time, with answers computed rather than stored.
  3. Labs graded on the result.Break-and-fix labs on a live Linux system. Security scenarios include containing a leaked cloud key traced through audit logs, cutting an over-permissive IAM policy to least privilege, hardening SSH without locking out a user, purging a leaked secret from Git history, and turning scan findings into a prioritized client report.
  4. Progress that reflects what's retained.Scores fade without review and guesses count for little, so the numbers show what I can still do, not how much time I spent.

Outcome

Secure and still workingA lab passes only when the fix closes the hole and the service still runs. Insecure and over-restrictive fixes are rejected.
Workplace practiceHelp desk tickets, a Linux terminal, a SQL console with a working database, and Security+ and Network+ practice exams.
Public outputMy Linux & Bandit flashcards are generated from SkillQuest and published on GitHub Pages.

How it was built

I designed SkillQuest, made the product decisions, and use it as my daily study system. The code was written with an AI pair programmer (Claude), and every change passes automated tests before release.

The problem

A community center serving English and Arabic speakers needed its production website to work in both languages. Arabic versions of existing content had to be created, and every change had to reach the live site without disrupting the people who rely on it.

What I shipped

  1. Accessible, responsive navigation.Works across screen sizes, by keyboard, and with screen readers.
  2. Reusable member components.One set of components shows the organization's members on every page that needs them, including the committee section in English and Arabic.
  3. A reviewed translation workflow.English content in the CMS is machine-translated into Arabic drafts. Guards keep every translation a draft until a person approves it.

Outcome

All four merged pull requests are live on acchouston.org after automated and in-browser testing. Machine translations stay drafts until a person approves them, the same change control production IT relies on.

CASE-003Trading strategy research lab

Oct 2026 · COMPLETE
Type
Personal research
Stack
Python · Docker
Method
Pre-registered, out-of-sample tests
Source
Private · walkthrough on request

The problem

Backtesting makes it easy to fool yourself: adjust the rules until the past looks good and you've measured luck, not an edge. The goal was to find out whether any strategy held up before real money was at risk.

What I built

  1. Rules before results.The evaluation protocol was fixed and reviewed before any strategy ran. The most recent data stayed sealed until candidates were frozen, and every test was checked on a period it had never seen.
  2. An audit trail.Every decision is logged with a date and reason. Changing a frozen rule requires a new, dated version.
  3. Safe by default.The lab runs offline with no API keys or account access, and live trading is blocked in configuration. A preflight check catches secrets committed to Git, and outside code is quarantined until it has been reviewed.
  4. Loss limits.Paper trading stops opening new positions for the week after a 3% weekly loss.

Outcome

  • No strategy beat simply buying and holding, so no money was put at risk.
  • A breakout strategy was profitable but trailed buy-and-hold, and was retired.
  • Two outside strategy ideas were tested and failed; an exploratory futures model was wiped out in every simulated scenario.
  • Findings were reported in plain language to a non-technical stakeholder.

How it was built

I owned the project: I set the goals, approved every decision and rule change, and wrote the reports. The code was written by AI coding agents (Codex and Claude) through pull requests I reviewed and approved.
