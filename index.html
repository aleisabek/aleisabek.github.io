CASE-001 · SkillQuest

The problem

I wanted daily practice tied to the jobs I'm applying for. Fixed question banks have a flaw: after a few passes you memorize the answers, not the skill. And a quiz score says nothing about whether you'd know what to do on a real broken machine.

Key decisions

  1. Generate questions instead of storing them.Subnetting, chmod, cron and CVSS problems are created fresh each time, so there's nothing to memorize.
  2. Don't let mastery be faked.Answers are marked "sure" or "guess", and a lucky guess barely moves the mastery score. A mistake only leaves the journal after I get it right on two different days.
  3. Practice the job, not just the exam.Help desk tickets, a terminal, a SQL console, and 8 Linux labs that break a system on purpose so I have to diagnose it, next to Security+ and Network+ practice exams mapped to the exam domains.

Verification: don't trust, verify

~175,000generated problems checked by the test suite for correct answers
SQLiteevery SQL challenge answer is run against a real database, not compared as text
8 labsa test runs every lab end to end: the broken system fails, a wrong fix is caught, the right fix passes

Known gaps (still open)

  • Security+ Domain 5 (security program management) isn't covered yet.
  • Advanced levels (3–4) aren't built yet.

How it was built

I designed SkillQuest, made the product decisions, and use it to study. The code was written with an AI pair programmer (Claude), and every change was tested before it went in.

CASE-002 · Trading strategy research lab

Oct 2026 · Status: ONGOING
Type
Personal research
Stack
Python · unittest · Docker
Scale
66 merged PRs · 1,046 tests
Source
Private · walkthrough on request

The problem

Testing trading ideas on historical data makes it easy to fool yourself: keep adjusting the rules until the past looks good, and you've measured luck, not an edge. I wanted to know whether any strategy really held up before a single dollar was at risk.

Key decisions

  1. Write the rules before seeing results.The evaluation protocol went through 4 reviewed versions before any strategy ran. The most recent months of data stay sealed until candidates are frozen, and every test develops on earlier data, then checks the next unseen period.
  2. Keep an audit trail.26 owner decisions are logged with dates and reasons. Changing a frozen rule means a new, dated version, never a quiet edit.
  3. Safe by default.The whole lab runs offline: no API keys, no account connection, and live trading blocked in configuration. A preflight check looks for secrets committed to Git, and outside code is quarantined and read without being run until it's audited.
  4. Limit the damage.Paper-trading runs have a risk gate: after a 3% weekly loss, new entries are blocked for the rest of the week.

Verification

1,046automated tests across data, strategy, and risk logic
66 PRsmerged, with written reviews and responses kept alongside the code
Benchmarkstrategies are measured against simply buying and holding

Findings, including the failures

  • A daily breakout strategy was profitable but far below buy-and-hold, so it was marked DEAD.
  • Two outside strategy ideas were registered, built, and tested. Both failed.
  • An exploratory futures model was liquidated in every scenario tested.

Results were written up in plain language for a non-technical stakeholder, trade by trade where it mattered.

Why it matters for security work

Assume you might be wrong, test against something you can't tune, keep secrets out of the code, and log every decision so someone else can audit it. That's the same discipline an incident review needs.

How it was built

I owned the project: set the goals, approved every decision and rule change, and wrote the plain-language reports. The code was written by AI coding agents (Codex and Claude), and changes went through pull requests with written reviews.

The problem

A community center serving English and Arabic speakers runs a production website that has to work in both languages. Arabic versions of existing content had to be created, and every change had to reach the live site without breaking it for the people who rely on it.

What I shipped: four merged pull requests

  1. Accessible, responsive navigation.Site navigation that works on any screen size and with a keyboard or screen reader.
  2. Reusable organization-member interfaces.Shared components for showing the organization's members, so the same pieces are reused instead of rebuilt per page.
  3. A localized committee section.The committee section in both English and Arabic.
  4. A guarded English-to-Arabic draft workflow in the CMS.Existing English content in Sanity is machine-translated into Arabic drafts, with guards so translations land as drafts for review instead of going straight to the live site.

Verification

The work was backed by extensive automated and browser-based testing, and all four pull requests were merged into the production site.

Why it matters for IT and security work

It's change management on a real production system: nothing reaches users without tests, review, and a safe default. Machine translation writes drafts, never live pages.

CASE-004 · Linux & Bandit flashcards

Started Sep 2026 · Status: IN PROGRESS

Live

The problem

OverTheWire's Bandit wargame teaches Linux by making you use it over SSH, level by level. I wanted a reference written in my own words: each card asks a plain question ("Where am I?", "Go up one folder") and answers it with the command.

Status

I've finished Bandit level 13 and I'm working on 14. The site has 190 cards in 12 topics, from finding and filtering files to encoding, archives, networking and git, with the PowerShell equivalent on the back where Windows has one. You can search, filter by topic, follow a spoiler-free Bandit study order, or drill one shuffled card at a time.

How it's built

The cards started as a hand-written page, and I kept a second copy in SkillQuest to study with spaced repetition. Two copies drift apart, so I made SkillQuest the only source: a Node.js export script reads its Linux deck and writes this site as one self-contained HTML file. Adding a card in the app and re-running the export updates the public page.

Known gaps (still open)

  • Bandit levels past 14 will need more cards as I reach them.
  • The public page has no spaced repetition; that part stays in SkillQuest.
